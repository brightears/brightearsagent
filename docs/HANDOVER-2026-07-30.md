### The three real bugs, in order of how bad they were

**1. Venue pitches shipped the model's rubric (`45825fa`).** The worst, because
pitches send from the **artist's own Gmail** to real venues and auto-send can fire
behind a 15-minute buffer. A real email went out containing
`"Word count: ~100. No prices, no exclamation marks, ... sign-off with first name
and act name."` Root cause was one character class: the existing strip was
`/^subject:[^\n]*\n+/i`, which **requires a trailing newline**, so when the model
returned everything on one line it silently did nothing.
**Transferable lesson: a guard that silently does nothing is worse than no guard,
because its presence stops anyone looking.** Worth grepping other model-output
sanitisers for `\n+` / `$` anchors with this in mind.

**2. Out-of-office stranded leads permanently (`fca0d11`).** No auto-reply
detection existed, so an OOO counted as a prospect reply → `ENGAGED` → sequence
stopped forever (nothing reopens a stopped run). Worse on the Hunt side: it
flipped `venue.status PITCHED → REPLIED`, and `lib/venues/follow-up.ts` requires
`PITCHED` for the +6-day bump, so a mail server cancelled the follow-up on a pitch
no human read.
**The existing eval described this bug and asserted it** — the `out-of-office`
journey's `why` said "one OOO permanently strands the lead" while its expectation
was `reply_attached`, the very flip that strands it. Fixed, plus a third step so it
can't drift back.

**3. Unroutable mail vanished (`7c136bf`).** `*.in.brightears.io` has a **wildcard
MX**, so Postmark accepts `leads@nobert.in...` as happily as `leads@norbert.in...`.
A typo'd forwarding address dropped real inquiries with nobody informed.

## 4. Email + DNS: verified state, and the landmines

**Outbound authentication is fully green.** Verified with a loopback probe, then
independently by mail-tester:

```
OUTBOUND_FROM = replies@mail.brightears.io
Return-Path   = pm_bounces@pm-bounces.mail.brightears.io  -> pm.mtasv.net
Received-SPF  : pass       DKIM: d=mail.brightears.io s=20260723080904pm
Both mechanisms pass AND align. mail-tester 10/10 on first-reply and follow-up.
```

**DNS changed today** (Namecheap, `brightears.io` zone only):

- **ADDED** `TXT @  v=spf1 include:_spf.google.com include:spf.mtasv.net ~all`
  — the apex had **no SPF at all**, so Workspace mail (including Vinyl's
  `support@brightears.io`, which sends via nodemailer + Gmail SMTP) was passing
  DMARC on DKIM alone. 2 of 10 lookups. `~all` not `-all` deliberately.
- **REMOVED** `resend._domainkey`, `default._domainkey`, and `TXT send`
  (`v=spf1 include:amazonses.com ~all`). Resend was genuinely dead — not a
  dependency in either `package.json`; every reference is archived docs. The
  `send` record mattered for security, not tidiness: it authorised *all of Amazon
  SES* to send as `*@send.brightears.io`, which aligns with `brightears.io` under
  relaxed DMARC — a live spoofing path.

**Rollback values for all three removed records:**
`../_handover-artifacts/dns-rollback-dkim.txt` (note: that file's "NOT removed"
line about `send` is stale — it *was* removed).

### Landmines

- **Never brute-force a DKIM selector.** Postmark's format is
  `<yyyymmddHHMMSS>pm` — a timestamp to the second. ~130 date guesses found
  nothing and led me to wrongly conclude DKIM was unpublished. Read it off a
  delivered message.
- **Postmark's `/messages/outbound/{id}/dump` is PRE-MTA.** DKIM-Signature and
  Return-Path are added on the way out, so their absence there proves nothing. I
  read it as failure and was wrong. The tell was that Return-Path was missing too.
- **DMARC passes on EITHER mechanism.** Check the one actually carrying the mail
  before declaring failure.
- **`/messages/inbound` needs BOTH `count` and `offset`** or it returns an error
  object with no `TotalCount`.
- **The login-free way to read real delivered headers:** send through the
  production Postmark server to `leads@<nonexistent-slug>.in.brightears.io` — the
  wildcard MX accepts it, no tenant claims it so nothing is created — then read
  `/messages/inbound/{id}/details`.
- **Before tightening DMARC to `quarantine`:** the apex carries **Vinyl's** mail.
  Verify Workspace + Postmark both still align, and watch the `rua` reports at
  `support@brightears.io` first.
- **Namecheap's Advanced DNS UI truncates:** it showed **5 of 18** records until
  "SHOW MORE" was clicked, and I nearly decided on the partial view. The Search box
  only filters rows already loaded — expand first, then filter to isolate a single
  row before clicking any trash icon. It also renders "No Records Found"
  intermittently after a write; trust `dig @dns1.registrar-servers.com`, not the UI.

## 5. The Google OAuth demo video

**Only remaining item for Google verification.** No CASA needed and no cost —
`gmail.send` is a *sensitive*, not *restricted*, scope. Console work is done:
consent screen published, branding verified with logo, scope declared.

**Why it matters beyond Google:** `app/api/oauth/google/start` has config guards
but **no per-user allowlist**, so any signed-up artist can start a Gmail connect
and will hit *"Google hasn't verified this app"* at the exact moment they decide
whether to trust us with their mailbox. Gmail sending is how the Hunt agent works,
so until verification completes a beta tester gets half the product.

**What is already captured** (`../_handover-artifacts/`):

- `oauth-consent-screen-capture.mov` — ~896s, the consent screen at **t≈277s**:
  *"Bright Ears wants to access your Google Account · Send email on your behalf"*,
  with the client ID and `gmail.send` scope readable in the URL bar.
- `oauth-scope-in-use-STALE-shows-bug.mov` — the scope in genuine use (Send test
  email → arrival), but **do not submit it**: it was recorded before `45825fa` and
  the email body shows the rubric leak. Re-record that ~30s segment; the pitch is
  clean now.

**The thing I got wrong, so you don't repeat it:** I assumed the *"Google hasn't
verified this app"* warning could be captured. It never appeared across two takes,
and I believe the reason is structural — **Google does not show that interstitial
to the Cloud project's own owner**, which `norbert@brightears.io` is. Revoking the
grant does not change it. Options: submit without it (the consent screen and client
ID *are* captured), or do one take signed in as a non-owner account. I'd try
submitting first.

Practical notes: `screencapture -v` with no `-V` records until you `kill -INT` it
(my first take died on a 5-minute limit mid-flow). The claude-in-chrome
extension's `save_to_disk` does **not** produce a file you can reach, so stitching
browser screenshots is not viable — record the screen instead. Verify the Chrome
window you're driving is on **this** machine before recording: front it with
`open -a "Google Chrome"` and compare against the page you just navigated to.

## 7. Two habits that paid off, worth keeping

**Click "Send test email" after any change to the pitch prompt or schema.** It
calls the real `generateVenuePitch`, so it is a genuine end-to-end probe of Hunt
output quality. The rubric-leak bug was found by watching a real email arrive —
not by reading code.

**Classify grep hits before drawing conclusions.** I found "resend" in 41 files of
the live agency stack and nearly refused a founder instruction on that basis.
Every hit was documentation; `resend` wasn't even a dependency. A raw match count
is not evidence of live usage — check the manifest and separate runtime from docs.
